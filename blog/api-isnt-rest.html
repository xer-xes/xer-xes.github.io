When the API Isn't REST: Reversing a Connect-RPC Frontend to Reach a Hidden Endpoint

2026-07-04  ·  web  ·  api  ·  recon

On Enigma, root came from a OliveTin instance running as root with an action whose password-typed argument was interpolated straight into a shell command — a clean command injection. The vulnerability took two minutes to spot. What actually cost me an hour was something dumber and more useful to write down: I couldn't figure out how to call the API. Every request I sent came back the same way, and the reason is a trap worth internalizing — modern web apps frequently don't speak REST at all.

The symptom: a field that's always empty

The exploit needed me to trigger an action by ID. The obvious REST-shaped call looked right and failed:

curl -s -X POST http://127.0.0.1:1337/api/StartAction \
  -H "Content-Type: application/json" \
  -d '{"actionId":"backup_database"}'

{"code":"not_found","message":"action with ID  not found"}

Read that error carefully — the crucial clue is the double space before "not found". If the ID had been wrong, it would say action with ID backup_database not found. Instead the ID arrives blank. The endpoint exists (it's not a 404), the handler runs, but it never sees my actionId. I tried every casing — action_id, actionName, id, path parameters, query strings — all blank. When a body field is universally ignored, the body isn't being parsed the way you think it is.

The cause: it's Connect RPC, not REST

The tell was in how the frontend was built. Grepping the compiled JS bundle for how the client is constructed:

grep -rhoE ".{60}window.client.{80}" assets/index-*.js

...o_({baseUrl: location.protocol+"//"+location.host+"/api/"});
   window.client = O0(a_, e); window.initResponse = await window.client.init({});

That createTransport({baseUrl}) + createClient(service, transport) shape is Connect RPC (the successor to gRPC-web). These apps look like they have a REST API — endpoints under /api/ that return JSON — but they are RPC methods generated from a protobuf schema. The URL is /api/<Method>, the body must match the protobuf message's field names, and unary JSON calls generally expect a protocol header. Miss any of that and the message deserializes to an empty struct — exactly the blank field I was seeing.

The fix: read the client, don't guess the server

The compiled frontend is the authoritative API documentation. It already knows the method names, the exact field names, and the transport. Two greps gave me everything:

# what methods does the client expose?
grep -rhoE "client\.[a-zA-Z]+\(" assets/*.js | sort -u
# ... startAction( getActionBinding( init( whoAmI( ...

# what object shape does startAction actually take?
grep -rhoE ".{40}startAction\(" assets/*.js
# ...const o={bindingId:w.bindingId, arguments:t, uniqueTrackingId:$()};
#    await window.client.startAction(o)

Two corrections fell out of that. First, the field is bindingId, not actionId — OliveTin references actions by their runtime binding, and the config id happens to be usable as one. Second, the request needs the Connect protocol header. I confirmed the calling convention against a harmless read method first (Init), then replayed it:

curl -s -X POST http://127.0.0.1:1337/api/StartAction \
  -H "Content-Type: application/json" \
  -H "Connect-Protocol-Version: 1" \
  -d '{"bindingId":"backup_database","arguments":[...]}'

{"executionTrackingId":"c29482bf-aad5-4f13-810c-a1c33c136c17"}

A tracking ID instead of a blank error — the message parsed, and root ran my command.

Recognizing this in the wild

Before you burn time crafting REST payloads, check whether you're even looking at REST. Signs you're facing Connect / gRPC-web / tRPC rather than a plain JSON API:

  • Every endpoint is POST, even reads, and paths look like verbs: /api/GetThings, /service/Method — not resource nouns like /api/things/42.
  • Request/response Content-Type is application/json, application/connect+json, or application/grpc-web+proto, sometimes with a Connect-Protocol-Version or grpc-* header.
  • The frontend bundle mentions @connectrpc, createPromiseClient, createConnectTransport, grpc-web, or @trpc.
  • A field you send is silently ignored and the server behaves as if the message were empty (schema mismatch, not a value error).

The methodology, generalized

  • Treat the compiled JS as the API spec. Minified isn't obfuscated — grep for client., method names, and the object literals passed into them. The exact wire field names are right there.
  • Calibrate on a benign method first. Get a harmless read call (init, whoAmI) working to nail down the transport and headers, then swap in the dangerous method with confidence.
  • Read error messages as oracles. A blank value in an error ("ID  not found") means a parsing/binding problem; an echoed value means the server read you and the value is simply wrong. Those two failure modes point in completely different directions.
  • Look for RPC methods the UI never calls. Once you speak the protocol, the service exposes every method in the schema — including ones with no button in the UI. "Not in the interface" is not "not callable."

The takeaway

The injection on Enigma was trivial; the real skill was refusing to accept "the exploit doesn't work" when the exploit was fine and my transport assumption was wrong. When an API won't answer, question the protocol before you question the payload — and let the frontend, which already knows how to talk to the server, teach you how.
