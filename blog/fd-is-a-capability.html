A File Descriptor Is a Capability: What SCM_RIGHTS Actually Hands Over

2026-07-19  ·  linux  ·  ipc  ·  privesc

On HackTheBox's Paperwork, a root-owned "security" daemon watched a log file for signs of abuse, and if it saw something bad, it politely sent an alert. That alert included, as an attachment, a live file descriptor into a root-only secrets file — opened by root, handed to whoever was listening. This post is about the mechanism that makes that possible, because it's a much bigger idea than one HTB box: in Unix, permission checks happen once, at open(). Everything after that is just a reference, and references are transferable.

The "security" feature that leaked root's password

At startup, paperwork-daemon (running as root) does this once and keeps the result for its entire lifetime:

admin_fd = os.open("/etc/paperwork/admin_pins.conf", os.O_RDONLY)   # root, at boot; file is 0600

Nothing unusual — plenty of daemons hold a config file open. The trouble starts in its incident-response path. On every connection to its management socket, it checks a log for suspicious commands; if it finds them, instead of just raising a flag, it does this:

def trigger_lockdown(conn):
    log_fd = os.open(LOG_PATH, os.O_RDONLY)
    evidence_bundle = array.array("i", [log_fd, admin_fd])
    conn.sendmsg([b"ALERT: SECURITY_VIOLATION..."],
                 [(socket.SOL_SOCKET, socket.SCM_RIGHTS, evidence_bundle)])

SCM_RIGHTS is ancillary data you can attach to a message sent over a Unix domain socket, and it does something no other IPC primitive does casually: it duplicates an open file descriptor into the receiving process's own descriptor table. The receiver doesn't get a copy of the bytes, and it doesn't get a path it then has to open() itself (which would trigger a fresh permission check). It gets the exact same kernel-level open file description root created — with root's access already baked in, permanently:

s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
s.connect("/run/paperwork/mgmt.sock")
msg, ancdata, flags, addr = s.recvmsg(4096, socket.CMSG_LEN(2 * 4))
for level, type_, data in ancdata:
    if type_ == socket.SCM_RIGHTS:
        fds = array.array("i"); fds.frombytes(data)

os.pread(fds[1], 4096, 0)
# b'ADMIN_PASSWORD=ApparelMortuaryCedar22'

The receiving user — archivist — has zero OS-level permission to read admin_pins.conf. It doesn't matter. The socket's own permissions (root:archivist, mode 0660) were the only real gate here, and they were built on an assumption: that only trustworthy, archivist-owned code would ever be the one connecting. That assumption held right up until archivist's own service turned out to have a completely unrelated path-traversal bug and got compromised first.

Why the check doesn't survive open()

This isn't a bug specific to this daemon — it's how the primitive is supposed to work, which is exactly why it's dangerous when it crosses a trust boundary by accident. A few things fall out of the same mechanic:

  • Discretionary access control is checked at open, not at read/write. The kernel evaluates permission bits (or ACLs) when a file description is created. Every subsequent read(), write(), or pread() on that same descriptor just uses the access already granted — there's no "are you still allowed to do this" re-check.
  • This is why setuid-root programs can drop privileges and keep working. Open your privileged files first, call setuid(getuid()), and the already-open descriptors keep functioning exactly as before. The privilege drop is real for anything not yet open — and irrelevant for anything that already is.
  • Passing the fd to another process is identical, just across a process boundary instead of a privilege-drop. SCM_RIGHTS gives the receiver a new descriptor number pointing at the same open file description. From the kernel's point of view, root already decided this file is readable; who's holding the descriptor now is not part of that decision.
  • "We only sent a reference, not the data" is not a mitigation. A reference to an already-open, already-authorized file is the data — and with an O_RDWR descriptor, it's write access too.

Where this shows up outside CTF boxes

Fd-passing is a legitimate, widely-used pattern — which is exactly why the mistake is easy to make. systemd's socket activation hands a bound listening socket from PID 1 to a freshly-started service over LISTEN_FDS. Container runtimes and privilege-separated daemons (OpenSSH's, sudo's, various browser sandboxes) pass fds across a fork to hand a lower-privileged worker exactly the resources it needs, no more. D-Bus and polkit make the same class of "who's allowed to be on the other end of this connection" decision that paperwork-daemon's socket permissions were trying to make. All of these are safe when the set of processes allowed to be on the other end is as trusted as the fd being sent — and unsafe the moment one of those processes has its own, unrelated attack surface.

Defending it

  • Don't pass a privileged fd to disclose information — send the information. If the goal was "show the evidence," read the bytes you intend to disclose server-side and send those, after making your own access-control decision about what's safe to reveal. A descriptor grants everything the file allows, not just the part you meant to show.
  • Audit every process allowed to connect to a privileged socket as if it already has whatever the socket can send. Unix permissions and SO_PEERCRED checks define who can connect — treat that set as your actual trust boundary, not the process that opened the file.
  • If a process in that trusted set has its own remote or local attack surface, your trust boundary now includes that attack surface too. archivist was "trusted" to talk to mgmt.sock — but archivist's JetDirect service was reachable and exploitable, so the boundary was really whoever could compromise JetDirect.
  • Review incident-response and "helpful" debug paths as carefully as normal logic. The lockdown/alerting branch here was clearly never held to the same scrutiny as the daemon's everyday behavior — which is common, because it's the code path everyone assumes never runs.
  • Treat SCM_RIGHTS usage as a loud, auditable event. It's rare enough in ordinary application code that a security-sensitive daemon sending or receiving ancillary rights data is itself worth alerting on.

The takeaway

Unix's permission model answers one question — can this file be opened — and answers it exactly once. Everything downstream of that trusts the descriptor, forever, no matter whose hands it ends up in. Socket activation, privilege separation, and "attach the evidence" code all rely on that same fact; the difference between a clean design and a privilege-escalation bug is entirely about who you let hold the descriptor afterward. Don't pass what you wouldn't paste.
