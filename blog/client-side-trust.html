The Client Is Not Your Server: When Encryption Keys Ship in JavaScript

2026-07-05  ·  web  ·  appsec  ·  htb-lessons

Rooting HackTheBox's MakeSense took a chain of four bugs, but the one that opened the door is a mistake I keep seeing in real code review: an application decided the browser should be responsible for security. It shipped an encryption key in JavaScript and did its input sanitisation client-side. This post is about why that class of decision is always fatal, and what "trust boundary" actually means once you strip the comforting abstractions away.

The anti-pattern, in one file

MakeSense's WordPress theme had a "leave a voice message" widget. It recorded audio, transcribed it in the browser with a local AI model, encrypted the result, and POSTed it to the server. The client-side wrapper contained this:

// whisper-wrapper.js — served to every visitor
const ENCRYPTION_KEY = 'bLs6z8iv3gWpsvyeabFosDjb4YQe7jdU13rI';

async encryptPayload(payload) {
  const keyMaterial = await crypto.subtle.digest('SHA-256', enc.encode(ENCRYPTION_KEY));
  const iv  = crypto.getRandomValues(new Uint8Array(12));
  const out = await crypto.subtle.encrypt({name:'AES-GCM', iv}, key, data);
  return base64( iv || out );   // IV || ciphertext || tag
}

The server received the blob, decrypted it with the same key, and trusted the plaintext as a legitimately-recorded message. The intent was obvious: "the payload is encrypted, so only our app could have produced it." But every ingredient of that encryption — the key, the algorithm, the IV construction, the wire format — was sitting in a file the server hands to anyone who asks for it.

So I never touched the microphone. I read the key out of the JS, replicated the format in ten lines of Python, and encrypted whatever I wanted:

KEY = hashlib.sha256(b'bLs6z8iv3gWpsvyeabFosDjb4YQe7jdU13rI').digest()
iv  = get_random_bytes(12)
ct, tag = AES.new(KEY, AES.MODE_GCM, nonce=iv).encrypt_and_digest(evil_payload)
blob = base64.b64encode(iv + ct + tag)     # the server accepts this happily

The "trusted" channel was a formality. And because the same theme also mapped spoken words to HTML symbols on the client — its own comment said "for XSS injection" — the payload I encrypted was a stored cross-site-scripting string. Encryption I controlled, wrapping sanitisation I controlled. Two locks, both with the key taped to the front.

Why "client-side" is never a control

The mental slip is treating the browser as part of your system. It isn't. The browser is the attacker's execution environment. Everything you send it — code, keys, validation rules, feature flags, "hidden" fields — is now data the attacker owns and can read, modify, replay, or ignore. Concretely, none of these is a security control:

  • A key or secret in JS or a mobile bundle. Minification and obfuscation are speed bumps; crypto.subtle calls and string constants are trivially recovered. A symmetric key you shipped is a public value.
  • Client-side validation and sanitisation. Length checks, regex filters, "disabled" buttons, HTML-escaping in JavaScript — all bypassed by talking to the API directly. Client validation is a UX feature; it improves error messages, nothing more.
  • Signing/encrypting in the client to "prove" origin. If the client can compute it, so can I. Provenance can only be established by something the client never sees — a server-held key, a session bound to an authenticated identity.
  • Hidden fields, price/role in the request, "internal" flags. If the server reads it from the request and trusts it, it's attacker-controlled input.

The one honest question to ask of any client-side mechanism is: "If the user rewrote this code, what breaks?" If the answer is "our security," it was never security.

What the client can legitimately do

Client-side crypto and validation aren't useless — they're just not trust mechanisms. They're fine for:

  • Confidentiality in transit beyond TLS, only with keys the server never holds — true end-to-end encryption, where the server is deliberately unable to read the data (e.g. a per-user key derived from a password that never leaves the device).
  • UX — instant feedback, fewer round-trips, optimistic UI.
  • Reducing load — pre-filtering obviously-bad input before it hits the API, in addition to server checks.

The tell for the anti-pattern is a shared secret: the moment the server needs the same key the client used, you've built obfuscation, not encryption. Real client-side confidentiality means the server can't decrypt — that's the whole point.

Defending it

  • Move every trust decision server-side. Decrypt, authenticate, authorise, validate, and output-encode on the server. Assume the request was crafted by hand, because it can be.
  • Never ship a secret you also verify against. If your architecture needs a shared key in the client, redesign it — use a server-side HMAC/signature the client can't forge, or a session bound to an authenticated user.
  • Treat "internal", "encrypted", and "signed by our app" payloads as untrusted input. They earn no exemption from validation.
  • Output-encode on render, everywhere — including admin and "internal" dashboards. The XSS in MakeSense fired against an automated admin. A CSP and context-aware encoding would have contained it regardless of how the data got in.
  • Threat-model the data flow, not the UI flow. Draw where bytes cross from a machine you control to one you don't. That line — not the network edge, not "logged-in vs not" — is your trust boundary.

The takeaway

"It's encrypted before it leaves the browser" and "the frontend won't allow that" are the same sentence dressed differently, and both answer the wrong question. The question isn't what your code does — it's what someone who replaced your code can do. Put the key, the check, and the decision on the server, and let the client be what it actually is: an untrusted, fully-inspectable, fully-rewritable window into your API.
