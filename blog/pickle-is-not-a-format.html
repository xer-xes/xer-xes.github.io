Every .pt File Is a .pickle File: Two RCEs From the Same Root Cause

2026-07-19  ·  python  ·  deserialization  ·  ml security

On HackTheBox's Bedside, the same bug got me in twice, wearing two different costumes. The foothold was a "PDF font resource" that turned out to be a pickle. The privilege escalation was a "model checkpoint" that turned out to be a pickle. Neither codebase thought of itself as doing deserialization — one thought it was parsing fonts, the other thought it was loading weights. That gap between what a format is called and what it does is the whole story.

Instance one: a CMap is not a CMap

pdfminer.six resolves a PDF font's /Encoding entry by treating it as a path to a CMap resource. CVE-2025-64512 is what happens when that resolution isn't constrained to the library's bundled CMap directory: point it somewhere else, and pdfminer reads the target bytes and hands them to pickle.loads(), with no check that the result is actually CMap data.

class RCE:
    def __init__(self, cmd): self.cmd = cmd
    def __reduce__(self): return (os.system, (self.cmd,))

gzip.compress(pickle.dumps(RCE(cmd)))   # this is the "CMap resource"

Nothing here parses a font encoding table. It's pickle.loads() wearing a .gz extension and a font-resource code path, reached by a completely unrelated feature — text extraction from an uploaded PDF.

Instance two: a checkpoint is not a checkpoint

The privilege escalation on the same box is a MONAI/PyTorch training script that sudo lets a low-privileged user run as root. Before training starts, it loads the most recently modified file in a checkpoint directory through MONAI's CheckpointLoader:

# monai/handlers/checkpoint_loader.py
checkpoint = torch.load(self.load_path, map_location=self.map_location, weights_only=False)

torch.save()/torch.load() are, underneath the model-training framing, a thin wrapper around pickle. A .pt file doesn't contain "tensors" in any format-constrained sense the way a JPEG contains pixels — it contains a pickle stream that, when replayed, issues instructions to reconstruct arbitrary Python objects, including a call to whatever __reduce__ says to call. PyTorch 2.6 made weights_only=True the default specifically because this had become a well-known attack class in the ML ecosystem — but MONAI's wrapper passes weights_only=False explicitly, so upgrading torch alone wouldn't have closed this one.

The pattern, not the CVE

Neither of these is really "a pdfminer bug" or "a MONAI bug" in isolation. They're the same bug: a codebase treats a byte stream as inert data because the surrounding code — a font loader, a training script — has no reason to think of itself as running a deserializer. Anything built on Python's pickle protocol has this property whether or not the API name says so:

  • pickle.load / pickle.loads — the obvious case
  • torch.load (pre-2.6 default, or any wrapper that passes weights_only=False)
  • joblib.load, dill.load — pickle-compatible by design
  • anything with its own "resource cache" that happens to use pickle internally for speed, the way pdfminer's CMap loader does

The file extension, the surrounding domain vocabulary ("font resource," "model checkpoint"), and the framework's own trust in its file format are all irrelevant to what actually executes. If the bytes came from a lower-trust source — an upload, a shared directory, anything not written by the same process reading it back — the question is never "is this a safe format," it's "does the loader call pickle anywhere in its call graph."

What actually helps

  • Prefer non-executable serialization formats for anything crossing a trust boundary. safetensors for model weights, JSON/protobuf for structured data — formats where the parser cannot be tricked into calling arbitrary code no matter what bytes it's given.
  • Don't trust a library default to survive a wrapper. torch.load's safer default is meaningless if something upstream of your call passes weights_only=False for you. Audit the actual call, not the framework's changelog.
  • Treat any directory writable by a lower-trust process as attacker-controlled input the moment something higher-privileged reads from it — regardless of whether that reader calls it a "cache," a "checkpoint," or a "resource."
